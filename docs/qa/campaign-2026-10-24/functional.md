## How it was run

- **The matrix's frame.** The catalog (`apps/web/src/lib/api-catalog/*.ts`: 1,231 doors in 60 files, here called *areas*) was dumped with each door's file, method, `access`, `limitedRoles`, `duties`, `module`, `feature` and `planFree`. A role's cell in an area is every door the catalog lets that role call (the catalog's own `permits` rule; OPERATOR for `operator` and `app-admin` doors, APPADMIN for `app-admin`, PUB for `anyone`). The gate in front of a cell is marked **m** (a school module), **f** (a platform feature), **p** (a plan the role must hold while it is active) or **d** (a duty on a FACULTY or HOD membership). "On the phone" is read off the phone's own source (`apps/mobile/src`, the `/api/v1/…` it calls): 647 of the 1,231 doors. The web's menus (`src/lib/nav.ts`) are what the page sweep walks, so the sweep's line stands for the nav.
- **Accounts.** ZZ fixture people, and demo.expert01 for its never-minted calendar feed, each by a session the run's own temporary scripts minted (userAgent `zz-walk`, the CLAUDE.md way) and deleted when the script ended. No login door, no password typed, no account made. Used: zz.admin, zz.principal, zz.teacher1/2/4, zz.pupil01/02, zz.parent01 and a second Northgate guardian, zz.driver01, zz.librarian, zz.warden, zz.alumni01/02 (ZZ Northgate); zz.admin.b, zz.teacher.b1 and a pupil (ZZ Southbank); zz.admin.c (ZZ Banyan); zz.cadmin, zz.cprincipal, zz.faculty01/02, zz.hod01, zz.examctrl, zz.iqac, zz.tpo, zz.accounts, zz.cstudent01/02, zz.cparent01, zz.calumni01 (ZZ Vidya College); zz.cadmin.d (ZZ Dhanvantari); zz.expert1, zz.recruiter01, zz.operator, zz.appadmin.
- **The harness.** Temporary scripts `apps/web/scripts/tmp-qa-func-*.ts` (a shared library and one script per suite), deleted at the end. Copies, every call (JSON lines: door, role, status, code, time) and every check with its evidence are in the coordinator's scratchpad under `functional/` (`scripts/`, `calls-*.jsonl`, `results-*.jsonl`, `contract-*.json`, the logs, `matrix.json`). Two kinds of pass:
  1. **The contract pass** — a copy of the API sweep's fixture resolver and actors (`scripts/api-sweep.ts`: the same samples and the same Northgate and Vidya actors) that calls **every GET door as every role the catalog permits** and parses the answer with the door's own `response` schema. The sweep asserts the status alone, and it never calls an `operator` or `app-admin` door as the operator or the content team (it only checks that each school role is refused): this pass did. Three runs: as found (features off), 1,597 calls; the college's doors again with college actors for ADMIN, PRINCIPAL, STUDENT, PARENT and ALUMNUS (ZZ Vidya), 453 calls; the feature doors' GETs while the features were on, 125 calls.
  2. **Behaviour suites**, one per kind the brief names (next section), each acting, reading the rows behind the answer on the admin connection, and putting back what it changed.
- **Platform features.** This layer switched **nothing**. At 08:05 UTC layer 4 switched all seven features and the three plans on for its own features pass (the operator's audit rows `operator.feature.on` at 08:04:59–08:05:03) and back off at about 08:14 UTC. This layer's feature suites and the feature-door contract pass ran inside that window (08:07–08:13 UTC) and left the switching to layer 4; the plans being active is why several feature checks met 402 PLAN_REQUIRED. At the end every feature read off and every plan inactive, as at the start.
- **Data.** ZZ Northgate, Southbank and Banyan; ZZ Vidya and Dhanvantari colleges; demo.expert01's calendar token. Every row made was named "ZZ QA …" and removed by id at the end of its own script (the list is under "What the run wrote"); `npm run zz:fixtures` was run once at the end, after the API sweep's chunk, as that run asks.

## Findings

### F-1 · Functional · Medium · Both · Fees: a guardian who has just paid online is told "Nothing is due to pay" when the gateway's webhook arrives at the same moment
- Accounts: zz.admin (a TEST gateway account saved for the run with values made by the script, removed after), zz.parent01 (guardian of zz.pupil01, Term 2 ₹12,500 open), on ZZ Northgate.
1. `POST /api/v1/fees/family/checkout {studentMembershipId, demandIds:[Term 2]}` as zz.parent01: 201, an order on the devbox gateway.
2. At the same moment, the checkout page's confirm (`POST /api/v1/fees/family/checkout/confirm` with the handler signature) and the gateway's signed `payment.captured` webhook for the same order (`POST /api/webhooks/razorpay/<schoolId>`) — Razorpay's ordinary flow, where the browser's handler and the webhook fire within milliseconds of each other.
- Expected: both answers 2xx; the one that loses is told `already`, as `settleOnlinePayment` promises ("a payment settles once, by whichever arrives first, and the rest are told already").
- Actual, 3 rounds of 3: the webhook `200 {"outcome":"settled"}`, the guardian's confirm **`403 "Nothing is due to pay."`**; one receipt, the payment PAID, the event processed. Two confirms at once (a double tap) behave the same: `[403, 200]`, one receipt. The money is right; the person who paid is shown a refusal right after paying, and on the phone or web that reads as a failed payment (a retry, a call to the office). Only the webhook-first order was seen; with the confirm first, the webhook's own throw inside the same path (the mechanism of E2E-A2) was not reproduced here.
- Cause: `settleOnlinePayment` reads the payment's status before any lock, then `settle` → `allocate` → `openDemands` locks the pupil's open demands and, finding them paid by the winner, throws `fees.refuseDemandsChanged`/"nothing due" instead of answering `already`.
- Fix: inside the transaction, lock the FeePayment row (`SELECT … FOR UPDATE`) and re-read its status first; PAID or REFUNDED → return `already` with the receipt. The same lock closes the webhook's side.
- Files: `apps/web/src/lib/fees-payments.ts` (`settleOnlinePayment` 373–391, `openDemands`/`allocate` 44–66, `confirmOnlineCheckout` 407–416), `apps/web/src/app/api/webhooks/razorpay/[schoolId]/route.ts`.

### F-2 · Functional · Low · Web · The operator's school edit stores a `javascript:` website and a contact e-mail that is not one
1. As zz.operator: `PATCH /api/v1/operator/schools/<ZZ Banyan> {"website":"javascript:alert(1)"}`, then `{"contactEmail":"not an email"}`.
- Expected: 422 for both, as the office's own form refuses them (`schoolDetailsSchema`: the website must start with http(s)://, the e-mail must be one).
- Actual: `200 {"ok":true}` both times; both stored (read back on the admin connection; put back to the fixture's values afterwards). The website is drawn as a link on the families' school page (`/explore/[schoolId]`, `href={school.website}`); the contact e-mail is where the platform writes to the school.
- Fix: validate the operator's body like the office's — `website` http(s) only, `contactEmail` an e-mail — in `operatorSchoolUpdateBodySchema`, and refuse anything but http(s) where `website` is rendered as a link.
- Files: `packages/contracts/src/v1/operator.ts:176` (`website: optionalText(300)`), `apps/web/src/lib/superuser.ts` (`updateSchool` ~326–328), `apps/web/src/lib/validation.ts:57` (the office's rule), `apps/web/src/app/(app)/explore/[schoolId]/page.tsx:108`.
- Untested: whether a browser would run the link (React and the CSP's `script-src` without `'unsafe-inline'` should both refuse it).

### F-3 · Functional · Low · Both · Dates and times that are not real are kept, ignored, or refused as "forbidden"
1. zz.teacher4: `POST /api/v1/account/prefs {channels, quietHours:{start:"25:99", end:"06:00"}}` → `200 {"ok":true}`, saved (put back after). The rule is `/^\d{1,2}:\d{2}$/` (`packages/contracts/src/v1/account.ts:13`); the quiet window then means whatever the push code makes of minute 1,599.
2. zz.admin: `GET /api/v1/fees/export/collections?fromKey=2026-10-24&toKey=2026-04-01` → 200, an empty sheet named `fees-collections-2026-10-24-to-2026-04-01.csv` — the office is handed a blank file rather than told the window is backwards (`feeExportQuerySchema`, `packages/contracts/src/v1/fees.ts:347`).
3. zz.principal: `GET /api/v1/principal/decisions?from=2026-13-01` → 200 with every decision: the impossible date passes the `\d{4}-\d{2}-\d{2}` pattern and the filter is silently dropped (`packages/contracts/src/v1/decisions.ts:22`).
4. zz.admin: `POST /api/v1/admin/calendar/closures` with the end before the start, and with `2027-02-30` → **403** `{"code":"FORBIDDEN"}` ("The end date cannot be before the start date", "Start date is not a real date"), where the catalog and every other door answer a bad input 422 — the class of BDD-2, here in `apps/web/src/lib/holidays.ts:293–297` (`AccessError`).
- Expected: 422 naming the field, for all four.
- Fix: a shared `dateKey` refinement that checks the calendar (and `hhmm` with 0–23 and 0–59), `fromKey ≤ toKey` refinements on the export and decision queries, and the closure checks as a coded 422 (`RuleRefusal` or `apiInvalid`) rather than `AccessError`.

### F-4 · Functional (contract) · Low · Both · Two doors are described otherwise than they behave

Files: `apps/web/src/lib/api-catalog/account.ts`, `packages/contracts/src/v1/account.ts:51–58`.
