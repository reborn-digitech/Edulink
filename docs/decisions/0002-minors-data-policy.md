# 0002 — Minors' data: what EduLink holds about a child, who sees it, and why

Status: accepted (Phase 6). Fulfils decision 4 of [0001](0001-mobile-monorepo-and-production.md).
Written from the code as it stands on 2026-09-08 — every row cites the file it was read from. Where the code does less than a policy should, the [Gaps](#gaps) section says so; nothing below is a promise the code does not keep.

## Frame

- **The school is the data fiduciary** (DPDP Act 2023 s.2(i)): every row about a pupil belongs to one school's tenant (`apps/web/prisma/schema.prisma` header; `apps/web/prisma/rls.sql`), the school's office creates the account or issues the code that does (`apps/web/src/lib/intake.ts`, `apps/web/src/app/join/actions.ts`), and only that school's staff, the child's own guardians and the child can read it. Whoever runs the server is a **processor** (s.2(k)): the operator flag opens exactly two tables, `School` and `Invite`, and never a child's marks (`User.isSuperuser` comment in the schema; `SUPERUSER_TABLES` in `apps/web/scripts/gen-rls.ts`); a look inside a school is a time-boxed, reasoned `OperatorAccess` row the school can see in its Safety Centre.
- **A child is anyone under 18** (s.2(f)). The code agrees: `isMinor = age < 18` (`apps/web/src/app/join/actions.ts:246`, `apps/web/src/lib/birthdate.ts`). `CONSENT_AGE = 13` (`apps/web/src/lib/constants.ts:339`) only sets a `needsConsent` flag in audit metadata — see Gaps.
- **Verifiable parental consent** (s.9(1)) is the guardianship. It is recorded as `Guardianship.consentSharingAt` / `consentNotificationsAt` (schema) and is set in exactly three places: a parent claiming the child with the student code **and** the child's date of birth as second factor (`apps/web/src/app/join/actions.ts` `claimChild`); a parent accepting the office's invitation, which the office cannot accept on their behalf (`apps/web/src/lib/parent-link.ts`, `apps/web/src/app/invite/[token]/actions.ts`); and the school's **stand-in guardianship** for a pupil no parent has claimed yet, revoked the moment a real parent arrives (`apps/web/src/lib/standin-guardian.ts`). A second, separate consent gates anything that sends a child's name out of the school: competition entries (`CompetitionEntry.parentConsentAt`, `giveConsent` in `apps/web/src/lib/competitions.ts`) and an outside mentor's first message (`apps/web/src/lib/mentoring.ts`).
- **No tracking, no behavioural monitoring, no targeted advertising** (s.9(3)): see [What the app does not do](#what-the-app-does-not-do). The DPDP Rules 2025 exempt educational institutions from parts of s.9 for educational activities and pupil safety (Fourth Schedule) — **counsel to confirm** the final text and that a school using EduLink is covered; this policy does not rely on it.
- Store guidance mapped: Apple App Review Guidelines 5.1.1 (data minimisation, consent), 5.1.2 (use and sharing), 5.1.4 (Kids: no personal or device information to third parties); the app is **not** submitted in the Kids Category (1.3). Google Play: Families policy (mixed audience), Data safety, Permissions, Account deletion. The store forms are answered row by row in `apps/mobile/store/privacy-answers.md`.

Access rules cited below: the row-level policies in `apps/web/prisma/rls.sql` (generated by `apps/web/scripts/gen-rls.ts`; `app.school_ids` per transaction, `app.user_id` for a person's own rows, `OWN_RECORD_READABLE` for a child's portable record); the application chokepoint `apps/web/src/lib/tenancy.ts` (`assertStudentAccess` — a teacher sees only pupils in a class they teach; `assertGuardianAccess` — an ACTIVE guardianship; `assertClassAccess`); the per-endpoint access lists in `apps/web/src/lib/api-catalog/*.ts`, which the OpenAPI document carries as `x-access` and the contract suite proves. "Office" below means ADMIN, and PRINCIPAL where the catalog lists it.

## Data inventory

Stored on the server means the Postgres database (`DATABASE_URL`); uploaded files sit under `STORAGE_DIR` on the server's disk or, when `STORAGE_BUCKET` is set, in an S3-compatible bucket the server alone holds the keys to (`apps/web/src/lib/storage.ts`, `blob-store.ts`). On the phone the only stores are: **expo-secure-store** for the keys in `KEYS` (`apps/mobile/src/lib/storage.ts`, `storage-platform.native.ts`); the **SQLite outbox** `edulink-outbox.db` for writes queued while offline, each row deleted the moment the server accepts it (`apps/mobile/src/lib/outbox.ts`, `outbox-platform.native.ts`); and **React Query in memory**, fresh for 5 minutes and dropped after 30 minutes unused or when the process ends (`apps/mobile/src/lib/query.ts`). Basis codes: **E** = the school processing for education under the guardianship consent above; **C** = a separate consent; **P** = the person's own preference; **S** = security and integrity of the service (s.8(5)).

## What the app does not do

Verified against `apps/mobile/package.json` and `apps/web/package.json` (no analytics, advertising, attribution, crash-SDK or social packages in either; the jest `transformIgnorePatterns` names `@sentry/react-native` as a boilerplate pattern only — it is not installed).

- **No advertising, no analytics, no tracking SDK, no behavioural profiling, no sale of data.** The only "adaptive" logic is the practice ladder in row 12, which serves the next question and nothing else.
- **No location** (EXIF GPS is stripped from photos on the server, row 11), **no contacts**, **no cross-app tracking**, no advertising identifier is read.
- **Every network destination the phone talks to:**
  1. the school's own API at `EXPO_PUBLIC_API_URL`, which a release build refuses unless it is `https://` (`apps/mobile/src/lib/api.ts`);
  2. **Expo's push service** — the phone asks Expo for a push token (`getExpoPushTokenAsync`) and the server posts notification titles and bodies to `https://exp.host/--/api/v2/push/send` (`apps/web/src/lib/expo-push.ts`), from where Apple (APNs) and Google (FCM) deliver them;
  3. **Expo's update service** `https://u.expo.dev/<EAS_PROJECT_ID>` for over-the-air JavaScript updates when a project id is configured (`apps/mobile/app.config.ts`, `expo-updates`);
  4. the system browser, opened only on `API_BASE` paths — SSO start and the web pages the app hands off to (`Linking.openURL` sites in `apps/mobile/src`, all prefixed with `API_BASE`).
- **Every third-party destination the server talks to:** the SSO providers on the web sign-in — Google, Microsoft, Apple as plain OIDC, no SDK, each present only when its env vars are (`apps/web/src/lib/sso.ts`; the phone's sign-in screen offers Google); the email transport — SMTP through nodemailer, whichever relay the deployment sets (`apps/web/src/lib/email.ts`); the SMS transport — Twilio by a form POST, no SDK (`apps/web/src/lib/sms.ts`); Web Push endpoints for browser subscriptions (`web-push`, `apps/web/src/lib/notify.ts`); and **Anthropic's API**, used by `apps/web/src/lib/translate.ts` to translate a **question-bank question** the content team types — the input is the question text, never a pupil's data, and it runs only when `ANTHROPIC_API_KEY` is set.

## What the app deliberately does not hold

Decided 2026-09-29, from the data audit's list of columns no table holds (docs/data-audit/README.md §4). A
column that is absent on purpose is written down here, so that its absence is not taken for an oversight
and filled.

| What | Decision | Why |
|---|---|---|
| Aadhaar number | Never held | As above: the UDISE+ sheet's two Aadhaar columns go out blank and the office enters them on the portal. |
| A bank account for scholarship transfer (DBT) | Never held | An account number beside a child's name is a target with no use inside the app; the scholarship portals take it from the family. |
| Caste certificate and income certificate numbers | Never held | The record holds the category and the income the family states; the certificate is shown to the office, which does not need the app to keep its number. |
| Disability certificate number and percentage; immunisation records | Not held | The record holds the UDISE+ impairment type and the health card holds what a teacher needs on the day. Nothing the app produces prints more. |
| A pupil's photograph | Not held | No paper the app prints carries one, and a photograph of every child is the most sensitive thing a school could store here. |
| Sibling links, transport route or stop, hostel or day scholar, house | Not held for now | No filing, certificate or receipt reads them. To be added when a feature needs one, with its own row above. |
| AAY, scholarships received, free uniform and textbooks, stream and vocational fields, mainstreamed date, alternate mobile | Left blank on the sheet | The office enters them on the portal. |
| A pass or fail, a promotion result, a rank | Deliberately not computed | The report card states marks and a band. The UDISE+ sheet states a pass only for a pupil who moved up with last year's card; a repeater's result is left for the office. |

Since the audit these were added and are no longer on its list: each parent's occupation and the family's
income, the previous school's TC number and date, the assigned roll number, a teacher's date of birth and
first day in service, the family's contact number, and up to three people to call on the health card.

## Child-specific rules on the phone

- **Permissions asked for** (`apps/mobile/app.json`): **notifications** (asked after sign-in, refusal is silent, `push.ts`) and the **camera** (asked at a pupil's first photo hand-in, refusal shows a way to the phone's settings and leaves the picker beside it, `camera.ts`). The camera, photo-library and Face ID permissions and their plugins that the foundations had declared were removed in Phase 6 once this inventory found no screen using them (Gap 1, closed); the camera returned with photo hand-ins, alone: `expo-image-picker` is configured with its photos and microphone permissions off, and Android's storage and media-read permissions are blocked in `app.json`, so nothing already on the phone is reachable through the app.
- **Screenshots and screen recording are refused** on the marks sheet and on exams/report cards (`expo-screen-capture` via `usePrivateScreen`, row 6–7).
- **A rooted or jailbroken phone is warned, not blocked** (`useRootedWarning` / `RootedBanner`, `apps/mobile/src/app/_layout.tsx`; strings `security.rootedTitle/Body` in the three dictionaries).
- **The session never leaves secure storage**: the token is read from expo-secure-store on each request and is not held in React state (`session.tsx`, `api.ts`); sign-out removes it, the session meta and the push registration, and calls `POST /api/v1/auth/logout` so the server row is revoked.
- **The pupil's channels are bounded**: messages to staff only (row 10), posts and comments reviewed before anyone sees them (row 11), remark threads not readable by the child (row 9), no private channel with an outside adult (row 16).
- **Nobody creates an account in the app**: sign-in is a password, a magic link, a school-issued first-sign-in code or Google SSO against an account that already exists (`apps/mobile/src/app/(auth)/index.tsx`; "SSO signs people in; it never signs them up", `sso.ts`).

## Rights and requests (DPDP ss.11–13)

- **See**: a guardian sees everything the school holds about the child in the parent views (`/parent/*` on the web, `/api/v1/family/*` on the phone); the child sees their own (`/student/*`, `/api/v1/family/student/*`); the report cards and certificates stay reachable after leaving at `/record` (`apps/web/src/app/account/page.tsx` → `account.recordAction`; `student-record.ts`).
- **Correct**: the child edits preferred name, avatar and bio at `/student/profile`; the office corrects name, class, date of birth and departure in the directory (`apps/web/src/app/(app)/admin/people/actions.ts`: `setBirthdateAction`, `recordLeaving`, `undoLeaving`); a teacher withdraws and reissues a report card; a grade edit is audited.
- **Choose**: a guardian sets which channels and quiet hours at `/parent/settings` (`POST /api/v1/family/settings`); anyone signs out other devices at `/account` (Devices tab).
- **Erase**: the request goes to the **school**, the fiduciary. The office ends the membership (`recordLeaving` — the record is kept, access ends the same moment) or, for an account with no history at all, removes it (`removeMembership`). The operator can remove a school without deleting anyone's records (`removeSchool`) or, on a typed confirmation, **delete a school entirely** with every row that cascades from it and the accounts that then belong to nothing (`deleteSchoolEntirely`, `superuser.ts`). There is **no self-service deletion** in the app or on the web — see Gaps and `ACCOUNT_DELETION_URL` in the store listing.
- **Grievance**: `SUPPORT_EMAIL` in the store listing; a problem report from the app (`More → Report a problem`, row 24) reaches the school's admins with a reference the person can quote.

## Gaps

Things a policy would like to say that the code does not yet do. Each is a decision or a ticket, not a sentence to soften.

1. **Closed in Phase 6 — permissions declared for features that are not in the code.** `app.json` carried camera, photo-library and Face ID purpose strings, the Android `CAMERA`, `USE_BIOMETRIC` and `USE_FINGERPRINT` permissions and the `expo-image-picker` and `expo-local-authentication` plugins, and no file under `apps/mobile/src` used any of them (hand-ins are text only; the phone cannot upload). The permissions, the plugins and the two modules were removed the day this inventory named them; `KEYS.lock` stays defined for the lock that is still to come. The camera permission and `expo-image-picker` returned later with photo hand-ins (row 8), under the rule this gap set: a permission is declared only by the feature that uses it, and the library permission is still not.
2. **Closed in Phase 6 — sign-out did not clear the outbox or the query cache.** `signOut` removed the token, the session meta and the push registration, and queued rows in `edulink-outbox.db` survived to be replayed under the *next* person's token on a shared phone; React Query's cache survived until it expired. `signOut` now clears the outbox (`clearQueue`, `outbox.ts`) and an unsent crash report before the token goes, and the root layout drops the query cache on the way to signed-out — pinned in `test/lib/session.test.tsx`. Still open in this gap: `expo-image`'s default cache keeps bulletin photos on disk after sign-out. A shared phone in a staff room is not an edge case.
3. **No retention period is enforced for the school's records** (rows 1–17): the code keeps marks, registers, hand-ins and messages indefinitely, by design ("a school is required to hold them long after the child has gone", `school-record.ts`). That is defensible only if the privacy policy says so and the school, as fiduciary, owns the schedule. The second half of this gap is closed: `retention:sweep` (`apps/web/src/lib/retention.ts`, nightly at 04:00) removes expired and revoked sessions and spent or lapsed sign-in tokens after a week, rate-limit buckets a day after their window, spent upload tickets after a month, the dev outbox after a month, job runs after ninety days keeping each job's last success, and audit rows — which also hold crash and problem reports — after two years, every count a `RETENTION_*` variable the operator may raise, and the audit horizon one they may set to 0 to keep the old promise. It touches none of rows 1–17.
4. **`CONSENT_AGE = 13` is a flag, not a gate.** The DPDP threshold is 18 and `isMinor` follows it, but nothing refuses a pupil under 13 (or 18) any action for want of a parent's consent: the stand-in guardianship gives the *school* the consenting seat until a parent claims the child. Whether that is verifiable parental consent under s.9(1), or rests on the educational-institution exemption in the Rules, is the question in checklist item 10.
5. **No self-service erasure or export.** The DPDP right to erasure (s.12) is met through the school and, at the platform level, only by the operator's whole-school deletion; there is no per-person data export. The parent welcome email says "you can unlink at any time from your settings" (`apps/web/src/lib/email.ts:354`) but `/parent/settings` has no unlink action — the only guardianship revocations are the stand-in's, the operator's and the departure's.
6. **Closed — uploads may live in a bucket.** `apps/web/src/lib/blob-store.ts` puts uploads in an S3-compatible bucket when `STORAGE_BUCKET` and the `STORAGE_S3_*` variables are set (`src/lib/s3.ts` signs the requests itself; no SDK), and on the server's disk under `STORAGE_DIR` otherwise. The bucket's own versioning or replication rule covers the uploads; the nightly dump covers the database. Row 18 of the network table above gains one destination when a bucket is configured: the bucket's endpoint, which receives the cleaned bytes and never a pupil's name.
7. **Session IP and user agent are stored** for every sign-in, including from the phone (`issueApiSession`, `apps/web/src/lib/api-v1.ts`), and the audit log records an IP with each action. Both are security context; the privacy policy has to name them.
8. **The Hindi and Marathi copy is not native-reviewed** (`packages/i18n/src/hi.ts` header says so of the app; the store listings in `apps/mobile/store/` inherit the caveat).
